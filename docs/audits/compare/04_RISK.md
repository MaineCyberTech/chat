## 7. Do-Not-Break Guardrails

1. **Auth must never break.** The `authenticate.ts:17-44` middleware is the gate for every authenticated operation. No changes to `apps/api/src/middleware/authenticate.ts`, `apps/web/lib/supabase/client.ts`, or `apps/web/app/api/v1/[...path]/route.ts` (BFF) without comprehensive test coverage first. The auth chain is: Supabase Auth → JWT → `authenticate.ts` → `req.userId`/`req.supabase` → RLS. Breaking any link = zero functionality.

2. **Service-role client must only be used where RLS bypass is truly needed.** Currently `getAdminOrAnon()` is used in 3 create paths (workspace, channel, message). These must be migrated to `req.supabase` (user-scoped) one at a time, with RLS policy verification before and after each migration. Do NOT change all 3 in one PR.

3. **Socket.io event contracts must be additive only.** Current event surfaces: `message:send`/`message:received`, `typing:start`/`typing:stop`, `user:presence`, `room:join`/`room:leave`. No event name may be renamed or removed. New events must use unique namespaces and must not interfere with existing event handlers. Both server (`socket.ts:28-49`) and client (`chat-view.tsx`) define handlers — both must be updated in lockstep.

4. **Caddy route mappings /v1/\* are contracts.** The 19+ route prefixes mounted at `/v1/*` in `app.ts:89-107` are contracts between Caddy, Express, and the frontend BFF. Changing a mount point requires coordinated updates to: `apps/api/src/app.ts`, `apps/web/app/api/v1/[...path]/route.ts` (BFF), `infra/docker/Caddyfile` + `Caddyfile.prod`, and `apps/web/lib/api.ts` base URL. Test all environments (dev, prod, local) before deploying.

5. **Database migrations must be additive only.** 48 migrations applied. Never DROP, ALTER COLUMN type, RENAME, or add NOT NULL without DEFAULT to existing columns after a migration has been applied to any environment. New migrations must be reviewed for lock risk — adding an index to a large table (`messages`) should use `CONCURRENTLY`. No destructive changes without a verified rollback script first.

6. **BFF proxy must preserve exact HTTP semantics.** The BFF (`route.ts:27-91`) must pass through: HTTP method, request body (JSON + FormData), query params, headers (Content-Type, Authorization), response status code, response body (JSON + non-JSON). The bare `catch` on line 85 must not lose error detail — currently it always returns 502 with no distinguishable error code. Any response transformation could break frontend error handling.

7. **The /metrics endpoint must remain authentication-gated.** `/metrics` (Prometheus) is behind `authenticate` middleware at `app.ts:113`. Exposing it unauthenticated would leak request volume, error rates, and business metrics. Any refactoring of the metrics middleware must preserve this gate.

8. **Rate limiters must keep composite key (user+IP).** The `authLimiter` and `searchLimiter` use `compositeKey()` at `rate-limit.ts:19` which combines `userId` and `ip`. Falling back to IP-only would allow an attacker who reuses an IP to bypass per-user limits. Mattermost uses IP-only limiting — our approach is stronger.

9. **Cross-origin CSRF protection must remain in place.** The `doubleSubmitCookieCsrf` middleware at `csrf.ts:70-110` includes an origin/referer check (defense-in-depth) plus token comparison with timing-safe equality. Both layers must be preserved. The CSRF cookie has `sameSite: "strict"` — if this is changed to `lax` or `none`, the origin check becomes critical.

10. **No simultaneous model-layer refactor and feature addition.** Changing the store abstraction (adding `IMessageStore`) at the same time as adding a new feature (e.g., pinned messages) creates unbounded risk. If the feature breaks, is it the store or the feature? Always separate infrastructure refactors from feature work by at least one release cycle.

11. **Production deploy workflow must remain idempotent.** `deploy-development.yml` and `deploy-production.yml` must be safe to re-run. `docker compose up` with existing containers should be a no-op for unchanged services. Adding `--force-recreate` (already present) is fine, but removing it could cause stale containers. Never use `docker compose down -v` which destroys volumes.

12. **CSP must remain restrictive.** Current CSP at `security-headers.ts:3-14` allows only `'self'` for scripts, with `'unsafe-inline'` only for styles. This is stricter than Mattermost's CSP approach (which allows `'unsafe-eval'` in dev mode and configurable frame ancestors). Any addition to `script-src` (e.g., for a CDN analytics script) must be reviewed for XSS risk. `'unsafe-inline'` for styles is acceptable but should be removed if/when all inline styles are migrated to CSS classes.

### Security Posture — Overall Assessment

**The current repo (Chat) has a stronger security posture in 6 of 10 dimensions** (auth flows, secrets management, HTTP headers, rate limiting, CSRF, dependency scanning), **equivalent in 2** (input validation, error handling), **and weaker in 2** (database access/RLS gaps being actively fixed, audit logging coverage).

The key advantage is the BFF architecture + same-domain routing + user-scoped Supabase clients, which together provide defense in depth that Mattermost's architecture doesn't replicate. The key disadvantage is audit logging coverage — Mattermost's more mature operational experience shows in broader event tracking.
